BLAKE2b headers node

A Bitcoin Knots BLAKE2b chain that lives in this browser. Headers: seeded from a checkpoint and a static file, verified with the schema engine, saved in IndexedDB, followed live over Nostr. Blocks: fetched from untrusted sources, verified against the header, cached under a byte budget. Sharing comes next. Unlinked experiment.

how this works

Seed: data/headers-<net>.json names a checkpoint (the last block shared with Bitcoin Core, a hard checkpoint in Knots) and data/headers-<net>.bin holds every header from eleven blocks before it to the tip at export time, 80 or 164 bytes each. The page verifies the checkpoint hash and runs every header rule over the whole chain (proof of work, linkage, difficulty with the fork adjustment, median time past, future time, version, timewarp, the fork rules) before keeping anything. Verified headers go to IndexedDB; on reload they are restored from there, re-verified, and only newer headers are fetched.

Live: the NIP-333 stream for the chain (kind 33333, twelve headers per event, signature checked). New headers that connect to the tip are validated against the stored chain and appended. If an event shows a different chain over recent heights, the branch with more work wins and the loser is dropped. Sources are never trusted; every header is verified locally.

Blocks: each block has a state — reference (header only), fetched (bytes obtained and verified in memory), cached (kept in IndexedDB, survives reload), shared (served to a peer; not yet), failed (no source produced bytes matching the header). Sources are asked in order: the static window in this repo (data/blocks/<net>/<hash>.bin), then mempool.guide's raw-block API. Bytes are accepted only if their header hashes to the expected block hash, the merkle root matches, and the structural rules pass. The cache is bounded (oldest blocks evicted first). This is the map a peer will later advertise.

Engine: bitcoin-desktop/schema@v0.0.25 via jsDelivr with the knots-blake2b overlay.
